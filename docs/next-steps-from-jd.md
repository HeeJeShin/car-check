### 계획과 달라진 점, 그 이유
- **Fly.io·Railway·AWS → Render + Neon**: 셋 다 이 프로젝트 규모에 맞는 무료 상시 요금제가 없습니다(Railway는 체험 크레딧만, Fly.io는 카드 등록 필요, AWS는 설정할 게 많고 프리 티어가 끝나면 과금). Render 무료는 15분 쉬면 잠드는 대신, 조회 화면을 Vercel ISR로 미리 만들어 둬서 사용자는 기다리지 않습니다. 리전은 셋 다 싱가포르로 맞췄습니다.
- **Docker 배포 → Render Blueprint(`render.yaml`)**: Docker는 로컬 DB에만 씁니다. Render가 Node를 직접 빌드하므로 Dockerfile이 필요 없었습니다.

## 1순위: 이력서에 바로 쓸 수 있고, 여러 공고에 겹치는 것

### 1. 관리자 로그인 + 권한 (README "다음 단계"에도 있음)
- **무엇**: `/admin`과 쓰기 API(POST·PATCH·DELETE)에 로그인을 붙입니다. JWT와 NestJS Guard를 쓰고, 역할은 `ADMIN`(검증 가능)과 `EDITOR`(초안만 작성)로 나눕니다.
- **왜**: 지금은 누구나 데이터를 바꿀 수 있습니다. WOKA는 "내부 운영자·제휴 매장 관리자", 트웰브랩스는 "인증·조직 관리", 메타엑스는 "병원 관리자 페이지"를 요구합니다.
- **이력서 문장 예**: "작성자와 검증자 권한을 나눠, 초안 작성자는 '검증됨'으로 바꿀 수 없게 서버에서 막았습니다."

### 2. 고질병 심사 흐름(상태 기반 로직) + 변경 이력
- **무엇**: 상태를 `DRAFT → IN_REVIEW → VERIFIED / REJECTED`로 늘립니다. 상태가 바뀔 때마다 누가·언제·왜 바꿨는지 `IssueHistory` 테이블에 남기고, 상태 변경과 이력 저장은 **하나의 트랜잭션**으로 묶습니다. 허용되지 않는 전이(DRAFT → VERIFIED 직행 등)는 서버에서 거절합니다.
- **왜**: WOKA는 "승인·심사 같은 상태 기반 비즈니스 로직"과 "트랜잭션·동시성"을 우대합니다. 지금 있는 DRAFT/VERIFIED 구조를 그대로 확장하면 됩니다.
- **테스트**: 상태 전이 표를 Vitest로 검증합니다(허용·거절 케이스).

### 3. AI 응답 스트리밍(SSE) + 대기·오류·재시도 화면
- **무엇**: `/ai/guide`를 SSE로 바꿔 답이 생성되는 대로 보여줍니다. 화면은 대기, 생성 중, 완료, 실패, 429 한도 초과("N초 뒤 다시") 상태를 각각 명확하게 보여주고, 재시도 버튼도 붙입니다.
- **왜**: 트웰브랩스는 "실시간 응답, 대기·오류·재시도", 메타팩토리는 "WebSocket/SSE 실시간 UI, AI 처리 상태"를 요구합니다. 이미 있는 429 제한과 자연스럽게 이어집니다.

### 4. E2E 테스트 + GitHub Actions CI
- **무엇**: Playwright로 핵심 흐름 2~3개를 테스트합니다(차종 검색 → 세대 선택 → 리포트, 관리자 초안 → 검증). PR마다 GitHub Actions에서 lint, 타입 체크, Vitest, Playwright를 돌리고, DB는 서비스 컨테이너로 띄웁니다.
- **왜**: 더즌은 "E2E 테스트", 메타팩토리는 "Playwright, CI/CD", WOKA는 "GitHub Actions"를 요구합니다. 실무에서 쓴 GitLab CI 경험과도 짝이 맞습니다.

### 5. 배포 + 에러 추적
- **무엇**: web은 Vercel에, api와 DB는 Docker로 Fly.io·Railway·AWS 중 하나에 올립니다. Sentry로 프론트와 백엔드 에러를 수집합니다.
- **왜**: 지금은 로컬에서만 돌아서 "실서비스"라고 말하기 어렵습니다. 배포 링크가 있어야 공고에서 말하는 "만든 것을 사용자 반응으로 회수"(브릿지웍스)를 보여줄 수 있습니다. Sentry는 메타팩토리와 워시스왓이 우대합니다.

## 2순위: 하면 이야기가 좋아지는 것

### 6. 매물 상식 검사 (README 아이디어)
- 연식·주행거리·가격을 입력하면 **코드가 규칙으로** 이상 신호를 계산합니다(예: 연식 대비 주행거리가 너무 적음, 시세보다 지나치게 쌈). AI는 결과를 쉬운 말로 풀어주는 일만 맡습니다.
- "계산은 코드, 해석은 AI"라는 원칙(4J, 소개 문단)을 한 번 더 보여주는 사례가 됩니다. 인딥에이아이·제로원에이아이처럼 AI 서비스 공고에서 쓰기 좋습니다.

### 7. 사용 지표 회수
- Vercel Analytics 이벤트로 차종 검색 수, 리포트 열람, 체크리스트 사용률, AI 가이드 사용률을 남깁니다.
- 기능 하나를 바꾸기 전과 후를 비교한 숫자가 하나라도 있으면, 브릿지웍스·페이타랩처럼 "결과로 확인하는 사람"을 찾는 공고에 바로 쓸 수 있습니다.

### 8. 모바일·매장 현장 사용성
- 매장에서 폰으로 보는 서비스라, 체크리스트를 PWA로 오프라인에서도 열리게 합니다(HomeCare PWA 경험 재사용).
- 터치 영역, 한 손 조작, 웹 접근성(대비, 라벨)을 점검합니다. 더즌·패스오더·워시스왓이 이런 점을 언급했습니다.

### 9. 캐시·요청 제한을 Redis로 이전 (+ 필요하면 BullMQ)
- 지금 README에도 "서버를 여러 대로 늘리면 Redis로 옮겨야 함"이라고 적혀 있습니다. 실제로 옮기면 WOKA와 어크로스비의 우대사항(Redis, 메시지 큐)을 채울 수 있습니다.
- 큐는 "출처 URL 유효성 주기 점검" 같은 배치 작업이 생길 때만 넣습니다. 억지로 넣지 않습니다.
