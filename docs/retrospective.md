# 중구(car-check) 회고: 1단계 (2026.10.10 ~ 10.27)

> 개발하면서 나눈 대화와 커밋 기록을 바탕으로 정리한 초안입니다. 느낀 점은 제 말로 다시 고쳐 쓸 예정입니다.

## 왜 이 주제였나
어떤 사이드 프로젝트를 할지 고민하다가, 너무 어려운 주제보다 **지금 당장 내가 가장 관심 있고 필요한 것**을 하기로 했다.
면허를 따고 차를 사고 싶어진 참이라, 관심사와 사이드 프로젝트를 합치면 시너지가 날 것 같았다.
"지금 내가 무슨 고민을 하고 있지?", "중고차를 사러 갈 때 가장 걱정되는 게 뭐지?"에서 출발하니 처음 접근은 어렵지 않았다.

## 무엇을 만들었나 (커밋 순서)
| 날짜 | 한 것 |
|---|---|
| 10.12 | 고질병 API + 화면 + Gemini 가이드 (NestJS·Prisma·PostgreSQL + Next.js) |
| 10.22 | 차종 선택·세대 선택·매장 점검 가이드 화면, 전기차 포함 차종 데이터 (시드 기준 차종 40개·세대 98개) |
| 10.26 | AI 캐시·요청 제한 → 조회 화면 ISR → 구글 로그인·역할 권한 → 고질병 심사 흐름·트랜잭션·동시성 → E2E·CI → 배포 준비·Sentry |
| 10.27 | **실제 배포**: Neon(DB) → Render(API) → Vercel(화면). 그랜저 스마트스트림 2.5 엔진오일 감소 고질병 추가 |

## 무엇이 어려웠나

**1. 배포에 필요한 서비스들의 역할**
Vercel, Render, Neon, Sentry, Google Cloud Console, GitHub Actions까지 하루에 여러 서비스를 연결하면서, 각 사이트가 무슨 일을 하는지 헷갈렸다. 특히 Neon(DB)과 Sentry(에러 알림)는 처음 보는 개념처럼 느껴졌다.
돌아보니 이전 회사에서는 DB와 서버를 인프라 담당이 미리 갖춰 두고, 나는 주소를 받아 개발에 집중했다. 그 "누군가 해주던 부분"을 이번에 처음 직접 맡은 것이었다.

**2. 설정하는 순서가 꼬이는 것**
Vercel 주소는 Vercel에 올려야 생기는데, Render(`WEB_ORIGIN`)와 구글 로그인 설정(승인된 원본)이 그 주소를 먼저 알아야 했다. 그래서 "Render 먼저 → Vercel → 주소를 다시 Render·구글에 넣기"라는 순서가 생겼다.

**3. 개발 환경에서 막힌 것**
- Node 22.13의 corepack이 서명 키가 오래돼 pnpm이 실행되지 않았다. corepack 대신 npm으로 pnpm을 설치하는 것으로 바꾸고 README에 남겼다.
- E2E에서 관리 화면에서 고친 내용이 사용자 화면에 바로 반영되지 않았다(ISR 캐시). 수정하면 캐시를 바로 지우도록 하고, 이전 테스트 실행의 캐시를 지우고 시작하게 고쳤다.

## 실제로 배포하며 겪은 것 (10.27)
설정 파일은 전날 다 만들어 뒀는데, 실제로 올리는 날에도 배울 게 많았다.

- **주소는 짐작하지 않는다.** Render 서비스 이름(`car-check-api`)을 이미 다른 사람이 쓰고 있어, 내 주소는 `car-check-api-vfyd.onrender.com`처럼 뒤에 글자가 붙었다. 짐작한 주소는 남의 서버였다. 대시보드에서 복사한 뒤 `/health`가 `{"ok":true}`인지로 확인했다. Vercel 주소도 마찬가지였다.
- **Neon 주소 두 개는 `-pooler`로 구분한다.** Connect 화면에 주소가 하나만 보여도, `-pooler`가 있으면 평소용(Pooled), 빼면 마이그레이션용(Direct)이다.
- **로컬용과 배포용 환경변수를 나란히 둔다.** 어느 값이 어디 들어가는지 헷갈려서 `api/.env`(로컬)·`api/.env.render`(Render), `web/.env`(로컬)·`web/.env.vercel`(Vercel)로 폴더마다 나란히 두고 저장소에는 올리지 않았다. `.env.production`이라는 이름은 로컬 빌드 때도 읽혀서 피했다.
- **운영 DB를 바꾸는 작업은 따로 다룬다.** 테이블 만들기와 샘플 데이터 넣기를 스크립트 하나로 묶어 직접 실행했다. 시드는 전부 지우고 다시 넣기 때문에, 관리 화면에서 승인한 데이터가 생긴 뒤에는 쓰면 안 된다.
- **마지막 연결은 CORS.** 화면 주소가 생긴 뒤 API의 `WEB_ORIGIN`에 알려줘야 브라우저에서 부르는 기능(AI 가이드, 관리 화면)이 열린다. 끝에 `/`를 붙이면 막힌다.

## 실무라면 무엇을 쓸까
지금은 사용자가 없는 단계라 **비용 0원으로 화면·API·DB·배포·에러 수집까지 전체 흐름을 직접 겪어 보는 것**이 목표였고, 그래서 무료 등급으로 골랐다.
실제 사용자가 있는 서비스라면 아래처럼 바꿀 것이다. (실무에서 직접 운영해 본 것은 GitLab CI·ArgoCD 배포까지이고, 나머지는 이번에 겪은 한계를 바탕으로 생각해 둔 선택이다.)

| 층 | 지금 (무료) | 실무라면 | 근거 |
|---|---|---|---|
| 화면 | Vercel Hobby | Vercel Pro, 또는 회사 클러스터에 컨테이너로 | Hobby는 개인·비상업용. 팀 권한·미리보기 배포·지원이 필요하고, 회사에 쿠버네티스가 있으면 같은 파이프라인으로 운영하는 게 일관됨 |
| API | Render 무료 | Render 유료 인스턴스, 또는 AWS ECS·회사 쿠버네티스 | 무료는 15분 쉬면 잠들어 첫 요청이 30초 걸림. 실사용이면 항상 켜져 있고, 여러 대로 늘리고, 무중단 배포가 돼야 함 |
| DB | Neon 무료 | AWS RDS(Aurora) PostgreSQL, 또는 Neon 유료 | 자동 백업·특정 시점 복구, 읽기 전용 복제본, API 서버와 같은 사설망 안에서 연결(지연·보안) |
| AI 캐시·요청 제한 | 서버 메모리 | Redis (ElastiCache 등) | 서버가 여러 대가 되면 메모리 캐시는 서로 공유되지 않음 |
| 에러 수집 | Sentry 무료 | Sentry 유료, 또는 Datadog처럼 로그·성능까지 보는 도구 + 슬랙 알림 | 무료는 이벤트 수 한도. 팀이 바로 알아야 하고, 에러만이 아니라 느려지는 것도 봐야 함 |
| 배포 흐름 | GitHub Actions → Render·Vercel 자동 배포 | 회사 표준 (예: GitLab CI → ArgoCD, 스테이징 → 운영 승인) | 이미 검증된 흐름과 롤백 방식을 따르는 게 안전. 운영 반영 전 확인 단계가 필요 |
| 비밀값 | 설정 파일을 대시보드에 복사 | 시크릿 매니저 (AWS Secrets Manager, Vault 등) | 사람이 손으로 복사하다 보면 노출된다. 이번에도 DB 비밀번호가 대화에 노출돼 바꿔야 했다 |
| 환경 | 운영 하나 | 개발 · 스테이징 · 운영 분리 | 운영 DB에 시드를 돌리는 것 같은 실수를 막으려면 확인용 환경이 따로 있어야 함 |

**고를 때 기준으로 삼을 것**
1. 사용자가 기다리지 않는가 (잠들기, 첫 요청 지연)
2. 데이터를 잃지 않는가 (백업, 복구)
3. 사용자가 늘면 여러 대로 늘릴 수 있는가
4. 팀·회사 표준과 맞는가 (이미 운영 중인 파이프라인, 보안 정책)
5. 비용이 그만한 가치가 있는가

**옮기기 쉽게 만들어 둔 부분**: DB는 PostgreSQL 표준이라 RDS로 옮겨도 연결 주소(`DATABASE_URL`)만 바뀐다. API(NestJS)와 화면(Next.js)도 특정 서비스 전용 기능을 거의 쓰지 않아, Dockerfile만 더하면 컨테이너로 큰 수정 없이 옮길 수 있다. (화면의 ISR 저장본은 서버를 여러 대로 늘리면 공유 저장소를 따로 맞춰야 한다.) 무료로 시작했지만, 실무 환경으로 옮길 때 코드를 다시 짤 필요는 없게 했다.

## 어떻게 접근했나
- **실무에서 못 해본 것을 기준으로 정했다.** 백엔드에서 요구되는 역량 중 실무에서 직접 해보지 못한 부분(서버·DB 설계, 인증, 테스트 자동화, 배포)을 이 서비스에 필요한 순서대로 만들었다.
- **모르는 건 역할부터 정리했다.** 사이트마다 "무엇을 하고, 어떤 값을 거기서 받아오는지"를 정리해 비밀값 메모 파일 맨 위에 적어 두었다. 다음에 설정할 때 이걸 보고 따라갈 수 있게.
- **아는 것과 비교했다.** 낯선 서비스를 회사에서 쓰던 방식(인프라 담당이 관리하던 DB, 사내 모니터링 도구)과 나란히 놓고 보니, 새로운 개념이 아니라 "직접 맡게 된 일"이라는 게 보였다.
- **고른 이유를 남겼다.** Fly.io·Railway·AWS 대신 Render + Neon을 고른 이유(무료로 계속 운영 가능한지), Sentry를 고른 이유(Next.js·NestJS를 공식 지원하고 무료 등급이 있음)를 문서에 적었다.
- **과장하지 않았다.** 배포 설정만 끝났을 때는 이력서에 "배포"를 쓰지 않았고, 10.27 실제로 올린 뒤에 사이트 주소와 함께 반영했다.

## 어떻게 익히고 있나
- **내가 실제로 쓸 서비스를 만들면서** 익힌다. 기능을 고를 때도 "중고차를 사러 갈 때 나라면 뭐가 필요하지?"를 기준으로 삼는다.
- **AI와 함께 만들되 "왜"를 묻는다.** 코드는 AI와 같이 쓰지만, 이해가 안 되는 건 "이건 왜 이렇게 하는지", "회사에서는 왜 안 썼는지"를 물어서 내 말로 바꿔 정리한다.
- **문서로 남기면서 정리한다.** README, 진행 상황 표, 회고처럼 적어 두면 무엇을 했고 무엇이 남았는지가 보인다.
- **포트폴리오에 옮기면서 다시 확인한다.** 한 일을 포트폴리오와 이력서에 쓰려고 하면, 실제로 한 것과 아직 안 한 것이 구분된다.
